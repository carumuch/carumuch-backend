# TiDD 티켓 템플릿

이 문서는 Codex가 현재 브랜치와 매칭되는 이슈를 기준으로 작업 티켓을 생성할 때 사용하는 템플릿입니다.

기본 원칙:

- 티켓 1개는 권장 커밋 1개에 대응합니다.
- 각 티켓은 하나의 명확한 작업 목적만 가집니다.
- 작업 범위와 작업 제외 범위를 분리해 과도한 변경을 방지합니다.
- 완료 조건과 검증 방법은 반드시 구체적으로 작성합니다.

---

## 작성 규칙

- 모든 항목은 실행 가능한 문장으로 작성합니다.
- `작업 범위`는 실제 수정 대상과 변경 의도를 함께 적습니다.
- `작업 제외 범위`는 이번 티켓에서 하지 않을 일을 분명히 적습니다.
- `완료 조건`은 체크리스트로 작성합니다.
- `검증 방법`은 실제 실행할 명령과 기대 결과를 함께 적습니다.
- `권장 커밋 메시지`는 이 티켓만으로 커밋할 수 있도록 작성합니다.

---

# TiDD 티켓

## 메타데이터

- 티켓 ID: `TICKET-XXX`
- 원본 이슈: `#000`
- 원본 브랜치: `type/000-branch-name`
- 상태: `TODO`
- 선행 티켓: `없음`

## 제목

한 줄로 작업 목적이 드러나게 작성합니다.

예시: 로그인 응답 DTO를 `UserInfoResponse`로 분리한다

## 목표

이 티켓으로 해결하려는 문제 또는 달성하려는 결과를 1~3문장으로 작성합니다.

## 작업 범위

- 수정할 클래스, 패키지, 설정, 테스트 범위를 구체적으로 작성합니다.
- 이 티켓에서 실제로 변경할 동작만 적습니다.

예시:

- `identity/presentation` 계층의 응답 DTO를 분리합니다.
- `AuthController`의 로그인 응답 조합 로직을 새 DTO로 이동합니다.
- 관련 단위 테스트를 함께 수정합니다.

## 작업 제외 범위

- 이번 티켓에서 하지 않을 작업을 명시합니다.
- 후속 티켓으로 넘길 항목이 있다면 분리해서 적습니다.

예시:

- 로그인 비즈니스 로직 변경은 포함하지 않습니다.
- 회원가입 응답 구조 변경은 포함하지 않습니다.

## 구현 메모

- 구현 시 따라야 할 제약이나 참고 사항을 작성합니다.
- 계층 책임, 기존 패턴, 주의할 의존성을 적습니다.

예시:

- controller는 DTO 변환만 담당하고 비즈니스 로직을 추가하지 않습니다.
- 새 DTO 네이밍은 `SomethingResponse` 규칙을 따릅니다.
- setter 대신 생성자 또는 정적 팩토리 메서드를 사용합니다.

## 예상 변경 파일

- `src/main/java/...`
- `src/test/java/...`

## 완료 조건

- [ ] 변경 목적이 코드에 반영되어 있습니다.
- [ ] 작업 범위를 벗어난 수정이 없습니다.
- [ ] 관련 테스트 또는 검증 코드가 함께 반영되어 있습니다.

## 검증 방법

- 명령어: `./scripts/verify.sh`
- 기대 결과: 관련 테스트가 통과하고 실패 메시지가 없습니다.

필요하다면 티켓 특화 검증을 추가합니다.

예시:

- 명령어: `./scripts/verify.sh`
- 기대 결과: 로그인 관련 테스트가 모두 통과합니다.

## 권장 커밋 메시지

`type: 작업 요약 #이슈번호`

예시:

`refactor: 로그인 응답 DTO 분리 #123`

## 비고

- 이 티켓을 분해하면서 생긴 가정이나 후속 티켓 메모를 작성합니다.

---

## 티켓 예시

```md
# TiDD 티켓

## 메타데이터

- 티켓 ID: `TICKET-001`
- 원본 이슈: `#123`
- 원본 브랜치: `refactor/123-separate-login-response`
- 상태: `TODO`
- 선행 티켓: `없음`

## 제목

로그인 응답 DTO를 전용 Response 객체로 분리한다

## 목표

로그인 API 응답 구조를 명확하게 분리해 controller 응답 조합 책임을 단순화합니다.
응답 DTO 네이밍과 계층 책임을 현재 코드 스타일에 맞춥니다.

## 작업 범위

- `AuthController`가 반환하는 로그인 응답 DTO를 전용 `Response` 타입으로 분리합니다.
- 기존 응답 조합 코드를 application 계층으로 옮기지 않고 presentation 계층 안에서 정리합니다.
- 관련 테스트와 API 응답 검증 코드를 함께 수정합니다.

## 작업 제외 범위

- 로그인 인증 로직 변경은 포함하지 않습니다.
- 토큰 발급 정책 변경은 포함하지 않습니다.

## 구현 메모

- 새 DTO 이름은 `LoginResponse` 또는 그에 준하는 명확한 이름을 사용합니다.
- 엔티티를 직접 API 응답으로 노출하지 않습니다.
- controller는 유스케이스 호출과 응답 변환만 담당합니다.

## 예상 변경 파일

- `src/main/java/com/carumuch/capstone/identity/presentation/AuthController.java`
- `src/main/java/com/carumuch/capstone/identity/presentation/dto/LoginResponse.java`
- `src/test/java/com/carumuch/capstone/identity/presentation/AuthControllerTest.java`

## 완료 조건

- [ ] 로그인 응답이 전용 DTO를 사용합니다.
- [ ] controller에 불필요한 응답 조합 코드가 남아 있지 않습니다.
- [ ] 관련 테스트가 새 응답 구조를 검증합니다.
- [ ] 이 변경만으로 독립 커밋이 가능합니다.

## 검증 방법

- 명령어: `./scripts/verify.sh`
- 기대 결과: 로그인 관련 테스트를 포함한 검증이 통과합니다.

## 권장 커밋 메시지

`refactor: 로그인 응답 DTO 분리 #123`

## 비고

- 회원가입 응답 DTO 정리는 별도 티켓으로 분리합니다.
```
